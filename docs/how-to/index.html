01 · Start here

Know which environment you are in #

Evaluation and production look similar, but the evidence is intentionally different. Before doing anything, identify the environment label in the lower-left workspace area.

Evaluation workspace

Learn with synthetic records

A local synthetic administrator, sample records, sample review cards, and simulated signing help demonstrate the lifecycle. Use synthetic documents only. These actions are not production evidence.

Production workspace

Work on customer-owned records

Your verified identity and active workspace membership control access. Documents, approvals, signature evidence, and audit events persist in the configured D1 and R2 resources. Missing configuration fails closed.

Do not put real contracts into evaluation mode.

Production use begins only after identity, storage, scanner, signature, delivery, records policy, monitoring, restore, and customer acceptance are complete. A green-looking screen is not go-live approval.

The five moves to remember #

  1. IntakeRequest, upload, or choose governed paper
  2. DraftSave the current working text
  3. ReviewCheck details and prepare exchange
  4. NegotiationRecord exact outbound and return
  5. SignatureSign the approved version
  6. ActiveOwn post-signature work
  • Confirm the workspace name, environment label, and your signed-in identity.
  • Check that the action you need is visible; Notice hides or disables actions your role cannot perform.
  • Open Today for ranked next actions or Contracts for the complete register.
  • If production has no records, use its five-step first-use panel—never expect sample parties to appear.

03 · Your first contract

Start from paper you have—or paper you need #

Three governed paths can create one contract record. Choose the path that matches the request and the source paper.

Generate

Start from a template

Use this when the business is preparing its own first draft. Choose an exact published governed version or a clearly marked ungoverned starter, bind business data, and review the saved working draft.

Import

Upload existing paper

Use this when a counterparty or colleague supplied a PDF, DOCX, RTF, or text file. Review every suggestion against the source before creating or linking the record.

Request

Complete published intake

Use this when an administrator published structured questions with an exact template-version and workflow pin. Submission freezes answers; human-confirmed conversion creates one linked contract.

Route A: start from a template #

  1. Select “Start from template”.

    Open it from Today, Contracts, Templates, global search, or press N when focus is not in a field.

  2. Choose contract direction.

    Customer contract, Supplier contract, or Company contract narrows the paper family.

  3. Choose the governance class.

    A published governed card shows its exact immutable version and digest. An ungoverned starter is useful scaffolding but is not automatically your company's approved legal paper.

  4. Enter the business context.

    Counterparty is required. Optional value uses a three-letter currency and supported zero-, two-, or three-decimal minor units; owner, department, governing law, structured entity/counterparty, published workflow, and an enabled CRM source provide context. Notice performs no FX conversion.

  5. Review before creating.

    Check the direction, exact paper class/version, fields, currency, references, workflow, and complete assembled text. Notice does not request approvals during intake.

  6. Open the working draft.

    Notice creates the contract record and immutable first working version together. Review and negotiate that exact paper before explicitly routing approvals.

Route B: upload existing paper #

  1. Select “Upload a contract”.

    Choose a PDF, DOCX, RTF, or text file up to 20 MiB. Notice inspects the complete bounded bytes instead of trusting the filename or MIME label: text must satisfy UTF-8/control rules, RTF must be balanced without binary/object payloads, PDF must have the expected header/trailer/xref and referenced-object structure, and DOCX must be a canonical bounded ZIP with safe consistent entries and required-OOXML-part structure. These checks do not replace malware scanning or human review. In production, clean files proceed; scanner-unavailable or inconclusive files remain quarantined; invalid or malicious content is rejected.

  2. Review the proposed fields.

    Confirm parties, direction, type, dates, value, payment/renewal text, governing law, tags, and review flags against the actual document. The analyzer has no extracted currency field, so an imported amount starts as USD; correct currency and amount in Contract details before risk review or routing. Suggestions are not legal conclusions or confidence scores.

  3. Correct what is wrong.

    Production performs bounded plain-text/RTF extraction in the Worker and limits PDF/DOCX parsing there to the structural checks above. It does not render those formats, extract their document text, or interpret their content or tracked changes: linking uses the deployment-selected customer-hosted OCR profile through the signed scanner gateway, or the explicitly disabled human-reviewed-text path.

  4. Create or link the record.

    Notice stores clean source bytes in private object storage with a hash and stores its metadata in the database. If readable text exists, it also creates an immutable first working version.

  5. Open the source safely.

    Download later only through the protected contract route. Deployment administrators select one customer-hosted OCR model/profile for the environment; individual uploaders get no model picker, and Notice hosts no model. Output is source-hash/profile bound but still needs comparison with the protected paper; an outage never falls back.

Route C: submit published intake #

  1. Open Request intake.

    Choose a published form and verify its version. Typed fields may include text, number, date, yes/no, single-select, or multi-select questions.

  2. Save and review the draft.

    Your request history keeps the draft, answers, and exact form version together while the form remains published. If an administrator retires the form, the history remains but the draft cannot be resumed; admins should resolve or communicate outstanding drafts first.

  3. Submit only when complete.

    Submission requires confirmation and freezes the answers. It does not make a legal or risk decision.

  4. Review as Legal/Admin.

    Confirm the exact form version, template-version pin when present, workflow choice, counterparty, direction, type, currency/amount, department, and reason. The signed-in reviewer becomes initial owner; structured entity/counterparty references are set afterward in Contract details. A Requester sees frozen history but cannot convert it.

  5. Convert or reject.

    Conversion atomically creates the Intake-stage agreement, initial snapshot, audit event, optional CRM event, and conversion link. It does not create working paper; add a source or save the first reviewed working version next. If the request should not proceed, Legal/Admin records a reason and confirms immutable rejection instead.

If upload or creation times out, retry the same intake.

Notice uses an idempotency key and same-tab recovery so a reload or timeout does not silently create a duplicate. Once agreement creation has been attempted, the intake fields stay frozen for an exact retry. Use Discard staged upload before creation only when the wrong file was selected. The abandoned protected source then remains eligible for guarded cleanup after seven days.

04 · The working paper

Treat the saved version as the contract—not the browser buffer #

Every contract workspace has four tabs. Together they separate current paper, negotiation evidence, authoritative details, and history.

Tab 1

Working draft

Current durable text, immutable versions, approved-clause insertion, linked source files, version number, and SHA-256.

Tab 2

Review & redlines

Production review rounds, returned-file states, human-review notes, line comparison, and promotion. Evaluation has sample clause cards only.

Tab 3

Contract details

Structured counterparty/entity, type, direction, department, minor-unit currency/amount, workflow, owner, dates, CRM label, risk, approvals, obligations, relationships, and admin records controls.

Tab 4

History & comments

Server-attributed workflow events, comments, hashes, export actions, and formal audit evidence.

Parties & related contracts adds structured roles and links such as master, order-under, amendment, DPA, renewal, and supersession without rewriting working paper. Removing a link requires a reason and confirmation and does not delete the underlying party, contract, paper, or audit evidence.

Edit and save safely #

  1. Wait for the latest version to load.

    Notice blocks editing and export if durable storage cannot load the authoritative paper. It never substitutes starter text as if that were current.

  2. Select “Edit working draft”.

    Your changes live only in the current browser tab until saved.

  3. Make the complete intended change.

    A legal or admin user can append an approved clause to the current editor buffer without discarding existing unsaved work; other permitted roles can read the library.

  4. Select “Save version”.

    Notice writes immutable content bytes, records the next version and SHA-256, advances the contract aggregate version, and appends an audit event.

  5. Confirm the new version and hash.

    The toolbar names the exact saved paper. If another user changed the record first, Notice asks you to reload rather than overwrite the newer version.

Unsaved work is not evidence.

Leaving the contract, switching tabs or contracts, or cancelling after editing opens a Save / Discard / Stay decision. Refreshing or closing the browser triggers its unsaved-changes warning. In Review & redlines, reviewed text and notes are also browser-only until you complete the review action.

Download the right thing #

  • Download saved draft (.txt) exports only the durable version named in the toolbar; it is disabled while unsaved editing is open.
  • Linked source documents download through the protected document route and retain their original filename and hash context.
  • Returned review files download from the selected submission in Review & redlines.
  • Audit evidence is a separate signed JSON envelope from History & comments; a text draft is not the audit package.

05 · Word & redlines

Use Word for the document review; use Notice for custody and decision #

Notice makes the exchange traceable: which exact bytes went out, which exact bytes came back, how the return was scanned, who reviewed it, and which reviewed text became the next working version.

Notice stores a DOCX, but does not automatically parse, apply, accept, or approve its tracked changes.

Notice does not parse Word Track Changes into clause decisions or accept them automatically. For a returned DOCX, a human must open the exact downloaded file in Microsoft Word or another customer-approved review environment and inspect tracked changes, comments, formatting, headers, footers, schedules, fields, hidden content, and the complete clean rendering. The browser line comparison uses only saved text and text you enter; it does not inspect the DOCX binary or make a legal verdict.

In Microsoft Word

Inspect the exact returned document, every tracked change and comment, complete formatting and schedules, hidden or field content, and the clean final reading.

↔

In Notice

Download the hash-bound return, record reviewed text and a review note, compare text at line level, then explicitly promote or reject the selected submission.

A complete review round #

  1. Save the complete proposed paper.

    Confirm the current working version, structured parties, type, direction, risk, currency/amount, workflow, and owner.

  2. Prepare one round.

    Notice permits one active round per contract. It copies the latest immutable working version—or an eligible clean source when no working version exists—records its full SHA-256, moves the contract to Negotiation, and prevents another active round or signature packet from using it concurrently.

  3. Verify the recipient outside Notice.

    Confirm the name and email using the business's approved contact process. Possession of a portal URL is not independent identity proof.

  4. Copy the temporary portal URL when it appears.

    It is shown when issued and is a bearer credential. The round stores only its hash; manual use does not let Notice redisplay plaintext after page state is lost. Share it only with the prepared counterparty. Rotation revokes the URL but does not reset that round's transfer budget.

  5. Send through an approved route.

    For a first wealth-management pilot, prefer manual delivery from the approved contracting mailbox and record the bounded provider/message reference. Automated delivery needs the scoped portal, configured delivery gateway, and separate negotiation-mail acceptance gate. While delivery is queued or processing, rotation, closure, and promotion remain blocked.

  6. Wait for a returned file.

    The portal accepts one file per submission. Signed inbound email, when separately enabled, can record zero through five attachments. Each file is capped at 20 MiB; the portal request is capped at 21 MiB. Across token rotations, one round admits at most 10 portal uploads: no more than 4 accepted returns, no more than 6 rejected/failed attempts, and no more than 96 MiB of cumulative multipart bytes. Only one five-minute upload/scan lease runs at a time. Downloads are capped at 20 attempts and 256 MiB. A busy response says to retry after five seconds; exhaustion requires staff to prepare a new round.

  7. Check the return state before opening anything.

    Only a clean, ready, policy-eligible submission on the latest active round can be promoted after human review. A portal submitter types an email address; a match is not authenticated identity or proof of mailbox control. Quarantined, rejected, sender-review, late, or no-attachment records require the specific remediation below.

  8. Download and review the exact source in Word.

    Do not work from an attachment in an old email thread or from a similarly named local copy. Use the protected file tied to the selected Notice submission and check its displayed hash.

  9. Enter the complete reviewed text and note.

    For exactly one attachment, supply plain text or Markdown that you personally reconciled to that file. Record who reviewed it, how Word/PDF features were checked, and why this is the intended working text.

  10. Promote deliberately—or reject.

    Promotion creates a new immutable working version, binds it to the return hash and review provenance, resolves the round, revokes the portal, invalidates old approvals, and clears signature readiness. Rejection or closure keeps the evidence without replacing the paper.

Choose the exchange route #

Recommended first pilot

Manual email + portal

Copy the temporary link, send it from the approved contracting mailbox, and record a bounded message/provider reference.

  • Simple operational start
  • Portal is the return route
  • Reference is an attestation, not delivery proof
After acceptance

Automated outbound

Notice queues a signed event to the configured delivery gateway with explicit recipient, subject, body, and scoped link.

  • No attachment bytes are claimed
  • Gateway acceptance is not recipient receipt
  • Terminal failure requires a fresh round
Optional integration

Inbound email capture

A dedicated domain and signed raw-body gateway route replies to a generated per-round alias.

  • Not required for portal use
  • Needs separate conformance evidence
  • Never auto-promotes clean attachments
Portal-link rules

Treat the URL like a temporary password. Do not paste it into CRM notes, ordinary tickets, chat, analytics, or the contract text. Rotation revokes the old URL immediately but does not reset the round's durable upload/download budgets. Closing or resolving the round revokes the current URL. An upload does not consume the URL by itself. Queued or processing automated delivery blocks rotation, closure, and promotion; wait for an accepted or terminal state. If leakage, wrong delivery, or transfer-budget exhaustion is suspected, follow the incident procedure—do not improvise a resend or bypass the round by rotating its token.

What the comparison can—and cannot—tell you #

  • It deterministically compares the saved current draft with the reviewed plain text or Markdown you entered.
  • It reports added, removed, and aligned unchanged lines, and may use coarse alignment for large edits.
  • It may display only the first 240 changed lines; review the complete texts.
  • No displayed differences means only that those two text inputs align line-for-line.
  • It does not inspect a binary attachment, prove there were no Word changes, apply a playbook, or make a legal, policy, risk, or acceptance decision.
Evaluation redline cards are demonstrations only.

The synthetic Accept/Reject clause cards and sample standard/fallback positions are not persisted production redline decisions. Production uses the controlled round, file, review, and promotion workflow described above. The separate Repository workspace searches extractor-registered fragments pinned to an immutable document version/hash; their source-text digest, offsets, and content are caller-supplied and must be checked against protected working paper. Human acceptance remains blocked from mutating contract data and is not a legal verdict.

06 · Approvals

Approve the exact paper—not the idea of the deal #

Notice binds approval work to the current immutable working version, its SHA-256, and the material contract basis. A promoted redline makes previous approvals stale and sends the current paper back through routing.

Required is not Pending #

Required

Routing is needed

The current contract must be approved, but no complete current request set exists yet.

Pending

Decisions are open

One or more requests tied to the current paper and basis await an authorized decision.

Approved

All current lanes passed

Every current approval request—including any additional current lane—is approved for this exact basis.

Governed workflow or compatibility policy #

A selected published workflow snapshots its exact definition digest and evaluated lanes onto the agreement. The bounded workflow contract supports one to twenty unique lanes, at least one unconditional lane, and ANDed conditions over direction, agreement type, department, risk/disposition, exact currency, and minimum/maximum minor-unit amount. That stored snapshot is authoritative for routing.

When no governed workflow is selected, the compatibility starter policy is:

ConditionServer-required approval lane
Every agreement explicitly routed for approvalLegal
Risk is High, assessment was waived, USD value is greater than 100,000, or any material non-USD value is recordedFinance in addition to Legal

Arbitrary extra labels cannot substitute for required lanes. Notice stores non-negative minor units plus an uppercase three-letter currency code using supported zero-, two-, and three-decimal mappings. It performs no FX conversion and never uses a cross-currency total for approval policy.

Authority is configured and rechecked—not inferred from a role label.

Direct-user or active-group authority must cover the exact lane and currency and may carry a minor-unit ceiling. A lane with no authority record at all uses the narrow compatibility mapping: admin/legal for Legal, admin/approver for Finance, and admin for another lane. Creating or revoking any record disables fallback for that lane; an unmatched user fails closed. Setup & access provides bounded builders and lifecycle actions, not an automatic legal conclusion or general no-code policy engine.

Request, claim, and decide #

  1. Finish negotiation and save the exact intended paper.

    Confirm version, SHA-256, counterparty, value, dates, and other material details.

  2. Assess the exact paper.

    Legal or Admin records Low, Medium, or High with a rationale and explicit confirmation against the displayed version, SHA-256, and basis. Only Admin may waive assessment, and a waiver conservatively requires both Legal and Finance.

  3. Use the stage-aware action to request approval.

    Requester, legal, and admin members can request the required lane set. Notice creates missing required requests atomically.

  4. Open the agreement before deciding.

    Read the current paper and Details, not an old email attachment or a remembered version.

  5. Claim only with real authority.

    The server checks active direct/group authority—or the no-record compatibility mapping—for the exact lane, currency, and amount, then repeats the predicate when committing. The requester cannot claim or decide the same request.

  6. Approve or Request changes.

    The decision, actor, time, exact-paper evidence, contract aggregate, and audit event persist. Every current request, including any additional current lane, must approve before the aggregate becomes Approved; each required lane needs a distinct attributable decider. Nobody—including legal or admin—can decide a request they created.

Send reminder queues reminder work; it does not mean an email was delivered. The scheduled outbox and configured delivery gateway handle external delivery and retries.

07 · Signature

Send only the approved immutable version #

Production signature uses the pinned DocuSeal 3.2.1 release and API contract 1.0.24. Notice validates a configured non-public, non-archived template, discovers its ordered signer roles, renders the verified working paper into a one-off document, and relies on provider email delivery—without exposing signer bearer URLs in the product.

  1. Confirm eligibility.

    The contract must be in Signature and all required approvals must still cover its exact working version, SHA-256, and material basis.

  2. Open the signature flow.

    Notice reads one to ten ordered roles from the configured DocuSeal template and requires at least one required signature or initials field for every role.

  3. Enter a name and a unique email for every role.

    Names need not be unique, but normalized signer emails must be. Provider-discovered roles are read-only, and the server rejects missing, duplicate, reordered, or substituted role/email sets.

  4. Create the secure packet once.

    Notice SHA-256 verifies the immutable working bytes, decodes and escapes the text/Markdown into a one-off HTML document, combines it with the approved signature-page/template, requests one merged artifact, applies the configured 1–720-hour expiration and email 2FA, and asks DocuSeal to send invitations.

  5. Refresh or reconcile—do not duplicate.

    If creation remains creating or signer state appears stale, use the available reconciliation/refresh action on the existing packet.

  6. Reconcile, then review the retained artifact.

    Notice requires exact signer identity/email and completed status for every expected signer, retrieves exactly one signed artifact, scans it, stores evidence, and stops at human review. Legal/Admin must confirm the exact artifact, paper hashes, version, and approved basis before activation.

Provider status is persisted, not silently polled.

Use Refresh provider state when a webhook needs reconciliation. If provider mapping did not finish, use Reconcile provider packet rather than creating another. After one hour, an admin may use the guarded absence check; an archived submission remains reserved unless a fresh provider check supports explicit supersession.

08 · Obligations

Turn signed promises into owned work #

Once a contract is Active or signature is completed, a permitted member can create one-time or recurring schedules, work their materialized occurrences, manage ownership and future generation, and complete each occurrence with immutable evidence.

  1. Open Post-signature tasks.

    Use Open, Complete, or All to focus the operating queue.

  2. Select “Add obligation”.

    Only eligible Active or completed contracts are offered.

  3. Describe the work and source.

    Use a concrete, action-led title and cite the governing clause or policy. Examples: “Send non-renewal notice”, “Collect updated SOC 2 report”, or “Review price uplift”.

  4. Choose an eligible owner, first due date, and recurrence.

    Use Once, Weekly, Monthly, Quarterly, or Annual with the IANA time zone, reminder lead days, and optional inclusive end date required by the operating policy. Calendar recurrence remains anchored to the original date.

  5. Manage the schedule deliberately.

    Legal/Admin can reassign it and all open occurrences, pause or resume future generation, or irreversibly end it with a reason and confirmation. Existing open occurrences stay actionable.

  6. Complete with evidence.

    The assigned owner records a ticket, confirmation, outcome, or other evidence note. A Legal/Admin override requires a reason. The result, evidence SHA-256, attribution, and audit event are immutable.

Obligation-write members create and manage schedules; eligible assigned owners may fulfill their own occurrences. Notice refuses to offboard an owner while active/paused schedules or open occurrences remain assigned. It does not infer obligations from the signed PDF; a human identifies, confirms, and governs the work.

09 · Portfolio, intake & reuse

See the estate, verify registered sources, and reuse only governed building blocks #

Server-backed portfolio/work, governed request intake, registered-fragment repository intelligence, global search, templates, and Approved clauses cover different jobs. The customer—not the software—still decides which content and judgment are authorized.

Portfolio & work #

The workspace work queue provides bounded live pagination for approvals, signatures, obligations, schedules, and attributable history. Search applies to the selected queue; Load more work follows an opaque tenant/query-bound cursor. Rows inserted after page one are excluded from that traversal, but status or sort-field updates can move existing rows between pages. Refresh from page one after acting on work. Portfolio insights aggregate the live workspace estate, including renewals, overdue work, lifecycle/risk distributions, and a separate value bucket for every currency. Notice performs no FX conversion and never shows a cross-currency value total.

Repository intelligence #

  • Literal search returns registered fragment text pinned to one immutable working-document ID/version/hash, including caller-supplied source-text digest/offsets and fragment digest. Notice does not derive or compare it with canonical working-paper bytes.
  • An externally created field proposal must carry confidence plus citations internally consistent with registered fragments. An authorized human opens the protected working paper, verifies every passage, then records a reason and accepts or rejects it.
  • The provider retains one UUID idempotency key with the exact proposal request. An exact retry recovers the committed proposal; different material under the same key conflicts instead of creating another record.
  • Even acceptance remains governed_executor_required and cannot mutate agreement or custom-field data. It is review evidence, not a legal verdict.
  • Ingestion batches are bounded, idempotent source inventories with hash/deduplication/link status. They do not upload files, perform OCR, migrate a repository, or invoke a broad executor.

Search two ways #

Global

Search everything or jump to…

Match counterparty, type, owner, department, CRM label, direction, stage, and tags. Quick actions open template intake, upload, or Approvals when permitted.

Local

Search this register…

On Contracts, combine the register query with direction, stage, risk, and sort. Reset clears only that register state.

Insert Approved clauses separately, review the working draft, and save a new version.

Initial governed-template and playbook creation atomically commits the parent, immutable draft version 1, durable retry receipt, and audit evidence. Parent-only creation is rejected. A different administrator publishes the exact digest. The browser drafts a later immutable revision only when a source version exists; historical empty-parent repair uses the protected version API/operator path.

The Contracts page can save the current bounded search, direction, stage, risk, and sort as a named private or shared view. Applying a view reloads its server-backed register from page one. Owners can remove their views; an administrator can remove another member's shared view only with the required reason and confirmation. Saved views are reusable live queries, not frozen report snapshots.

Integrations without browser-held secrets #

The Integrations area explains Salesforce, HubSpot, and signed custom-webhook destinations behind the separately deployed first-party CRM gateway. The main Notice Worker emits canonical events with independent mail and CRM delivery state. The gateway owns durable receipts, retry, replay/collision protection, version fencing, provider adapters, and redacted recovery operations.

  • Provider credentials and customer field mappings belong in the CRM gateway deployment, never in the browser or main Notice Worker.
  • An admin sees redacted status and can run harmless configured-service diagnostics from Setup & access.
  • CRM is optional. Disable it until the contract workflow is accepted if it is not needed for the pilot.
  • Record-at-a-time CRM resync, tombstone, and legacy-cleanup controls are maintenance tools with strict evidence requirements, not a general bulk console.

For deployment and mapping detail, use the included CRM gateway guide.

10 · History & evidence

Record what happened—and preserve proof outside the app when policy requires it #

History & comments combines human context with server-attributed workflow events. Formal exports add integrity evidence, but custody and retention remain customer responsibilities.

Comments and workflow events #

  • Members with comment permission can append a comment; actor and time come from the server session.
  • Lifecycle, document, approval, signature, negotiation, export, and records actions append workflow evidence.
  • Agreement events form a gap-checked hash chain. A chain failure blocks evidence export.
  • Use comments for plain-language context, not secrets, temporary portal URLs, or unsupported claims of approval.

Agreement evidence export #

A member with audit-read permission can download a signed JSON evidence envelope containing the contract record, approval history, document-version hashes, signature evidence, verified audit-chain head, and any exact source-attributed agent plan, decision, and execution evidence. Every contributing D1 record is read from one transactional snapshot before signing, and a dangling attribution blocks export. Production export requires the configured independent audit-signing key. Retrieve binary objects separately and verify their size and SHA-256 against the signed snapshot.

Workspace and offboarding export #

An admin can download a signed JSON record with sanitized purge and integration history, a referentially closed service-principal/grant/run/plan/decision/execution ledger, and an artifact manifest. Storage keys and errors from purge jobs, secret-backed diagnostic fingerprints/detail, and idempotency-key material are omitted. Document binaries remain separate and must be retrieved through protected routes and verified against declared size and SHA-256.

An export download is not automatically an archive.

Store required evidence in protected independent storage, verify its payload hash and HMAC with controlled key access, record the source revision and chain head, and apply the customer's retention and custody policy. Hash chains do not by themselves reveal deletion of the latest event without a previously retained head or export.

Retention and legal hold #

Admins see retention and legal-hold controls on Contract details. Every change requires a reason. A legal hold overrides automated deletion, and agreement policy can cascade to linked documents. The customer chooses the schedule, deletion authority, backup expiry, evidence retention, and offboarding process; Notice supplies controlled mechanisms, not legal advice.

Workflow-specific retry patterns #

Generate / import

Retry exact intake

The same-tab idempotency record protects against duplicate creation. Do not change frozen fields after a write was attempted.

Working draft

Reload on conflict

Reconcile your local text with the newer saved version. Notice will not silently overwrite someone else's save.

Review round

Refresh eligibility

A stale, closed, resolved, rotated, or changed round needs current state. Terminal automated delivery failure requires closing and preparing a new round.

Signature

Reconcile, don't recreate

A provider may have accepted the packet even when mapping failed. Refresh or reconcile the existing packet.

Mail / CRM outbox

Let durable delivery finish

Queued, processing, accepted, and dead are distinct. One successful sink does not mask another failed sink.

Scanner outage

Keep quarantine intact

A returned review file has an authorized in-product rescan path that claims one exact source before scanner work; a correlated malicious result remains authoritative even if a clean result races it. Initial-import quarantine requires the documented protected API/operator path; the import dialog has no rescan action. Never replace bytes or hand-edit status.

When escalating, share references—not contract contents.

Capture the visible error, request ID, approximate time, environment, workspace, contract/round/packet identifier, action attempted, and whether the issue is repeatable. Follow the customer's secure support and incident channel for any sensitive content.

12 · Admin & setup

The product is off the shelf; production is still customer-owned #

Most remaining work is repeatable installation, not unfinished CLM engineering. A business should be able to hand this repository to an implementation partner, supply its choices, and receive an accepted deployment without redesigning intake, negotiation, approval, signature, or obligations.

What an admin can do in Notice #

  • Review technical preflight and customer-configuration gates.
  • See redacted DocuSeal, scanner, delivery, optional inbound email, and optional CRM status.
  • Run harmless live diagnostics for configured services using server-managed secrets. Optional DocuSeal MCP validates initialize, exact HTTP 202 for notifications/initialized, and tools/list, then calls only read-only load_template to cross-check the configured template and ordered roles; mutation tools remain blocked.
  • Invite a verified email, assign one of five roles, enable or disable access, and preserve the last active administrator.
  • Create and inventory legal entities, counterparties, manual groups, typed custom-field definitions, governed templates/workflows/intake forms/playbooks, and direct/group currency-and-amount lane authority.
  • Register or disable service principals, issue or revoke bounded human-sponsored grants, and review the exact governed plan inbox. A sponsor cannot approve or reject their own plan; a different active Admin must decide it. Executable reads repeat exact authority, expiry, agreement-version, and latest-paper checks at claim and completion. See the governed agent API.
  • Refresh readiness evidence, manage contract retention/holds, and export workspace/offboarding manifests.
  • Use strict, record-at-a-time CRM reconciliation controls when required.
The admin screen does not create production infrastructure or invent policy.

It cannot create provider accounts, enter deployment secrets, configure the protected identity edge, decide the customer's legal positions or authority matrix, synchronize IdP groups through SCIM, set corporate records policy without an approved decision, or approve go-live. Those choices belong to the customer's implementation and governance process.

Recommended path to staging and production #

  1. Select an exact reviewed source revision.

    Retain the matching remote CI, dependency/security evidence, SBOM, approvals, and publication boundary.

  2. Use the staging deployment plan.

    Copy the supplied example manifest to an ignored customer/environment file, validate it, review the redacted plan, and keep secrets out of source.

  3. Provision isolated Cloudflare resources.

    Use explicit custom routes with Workers Paid, private D1/R2, disabled default/preview URLs, and separate staging/production resources.

  4. Connect identity and bootstrap two admins.

    Prefer Cloudflare Access application JWT validation. Keep bootstrap elevation temporary, then disable it and clear the bootstrap email list.

  5. Configure enterprise governance.

    Load legal entities, counterparties, groups, custom fields, templates, workflows, intake forms, playbooks, and exact lane/currency/amount authorities; independently publish and test the immutable versions.

  6. Connect mandatory providers.

    Configure scanner, delivery gateway, DocuSeal, scheduled jobs, and monitoring. Add inbound email or CRM only when deliberately selected and accepted.

  7. Run readiness and live diagnostics.

    The protected report must be green, but it is technical preflight—not legal, security, records, or business acceptance.

  8. Complete the synthetic acceptance journey.

    Prove generate/import, a portal/Word round, reapproval, exact signature, obligation, export, retention/hold, identity isolation, negative paths, backup, and restore.

  9. Obtain customer authorization for real data.

    Record named approval for policies, paper, people, providers, residual risks, and production use.

A sensible first wealth-management scope #

The repository's wealth-management starter profile recommends one legal entity, one workspace, and one centrally managed contracting team. Start with vendor and commercial agreements such as mutual NDAs, software subscriptions, professional/supplier services, order forms, and linked DPAs. Defer client advisory agreements, account-opening/custody/trading instructions, fund subscription documents, regulatory filings, and autonomous legal conclusions until separately designed and approved.

13 · Troubleshooting

Common symptoms and the safest next move #

Start with the visible state and current record. Avoid changing database rows, resending old credentials, creating duplicate signature packets, or bypassing quarantine.

I cannot see the upload, edit, redline, approval, or admin action.

Your server-derived role may not include that permission, the record may be in an ineligible stage, or required durable/provider state may not be ready. Confirm your role, open the exact record, and ask an admin for the least-privilege access or owner action needed. Browser changes cannot grant authority.

The imported or returned file is quarantined.

Do not download or promote it. A scanner outage or inconclusive result must remain isolated. A returned review file exposes the authorized in-product rescan action after scanner recovery. That action serializes one exact source under a lease; a correlated malicious verdict dominates a concurrently clean outcome. Initial-import quarantine requires the documented protected API/operator path; there is no rescan action in the import dialog. A clean result advances the same object and lineage, while a malicious result remains rejected and follows guarded cleanup.

The temporary portal link was lost, expired, or may have leaked.

Do not search logs, CRM, tickets, or old emails for plaintext. If the round is active and delivery state permits it, rotate the link; the old one stops working, but the round's upload/download budgets do not reset. If automated delivery is still queued/processing, wait. If the round is closed/resolved or delivery is terminal-dead, close as needed and prepare a fresh round from the current immutable paper.

The portal says upload busy or transfer limit reached.

Upload busy means another request holds the round's one upload/scan lease; wait at least the returned five-second interval and retry once. Transfer limit reached means a durable per-round count or byte budget is exhausted. Rotation cannot reset it: ask the sender to close or resolve the old round and prepare a new one.

The counterparty says they replied by email, but Notice shows no file.

Inbound email capture is optional. If the round has no generated reply alias, the intended return path is the portal. If capture is enabled, inspect provider/gateway delivery, exact alias, authentication, replay/collision and no-attachment evidence without forwarding the raw contract through an unapproved channel.

The gateway delivery is queued, processing, or dead.

Queued/processing is not final; wait for the scheduled outbox to record acceptance or terminal failure. Gateway acceptance does not prove counterparty receipt. A terminal-dead negotiation event has scrubbed the plaintext portal URL from that durable delivery payload, so the event cannot be resent; the round token itself is not single-use. Close the round, confirm recipient details, and prepare a new round.

Approval says Required again after I promoted a return.

That is expected. Promotion creates a new immutable working version, making earlier approval evidence stale and clearing signature readiness. Confirm the new version/hash and explicitly route the required lanes again.

I approved a lane, but the contract is still Pending.

Another required current lane may still be pending. The aggregate becomes Approved only after every lane in the stored governed-workflow snapshot—or the compatibility required set—is approved by distinct attributable deciders. Under the compatibility policy, High risk, a waiver, USD value above 100,000, or any material non-USD value requires both Legal and Finance.

Signature creation failed or the packet looks stale.

Do not create a second packet. Reload Signatures and use Reconcile provider packet or Refresh provider state on the existing record. If a fresh reconciliation is already processing, retry later. Admin recovery actions are intentionally narrow and require fresh provider checks.

I downloaded a draft but it does not include my edit.

Draft download exports only the exact durable saved version and is disabled during normal unsaved editing. Save a new version first, confirm the displayed version/hash, then download that version.

Setup says the workspace is not ready for production.

Open the redacted preflight and provider diagnostics as an admin. A missing customer decision, provider endpoint/credential, exact supported provider slug, storage/identity configuration, or acceptance attestation keeps the deployment fail-closed. Follow the linked remediation in Production setup; never mark a gate true without retained evidence.

The mobile menu or contract layout feels different.

The same lifecycle and counts remain available. Use the menu button, close it with the X, scrim, or Escape, and horizontally scroll the stage rail when needed. Contract rows stack into cards while preserving separate checkbox, record, action, and queue targets.

14 · Quick reference

The one-page operating checklist #

Print this section or keep it beside the first few agreements.

Before intake #

  • Confirm this is the correct production workspace and that real-data use is approved.
  • Choose a published request form, an exact governed template version, a clearly marked ungoverned starter, or upload for existing counterparty/company paper.
  • Use only supported file types and no file larger than 20 MiB.
  • Confirm structured counterparty/entity, direction, type, owner, department, dates, risk, three-letter currency, minor-unit amount, and selected workflow.
  • Save and note the exact working version and SHA-256.

Before counterparty exchange #

  • Verify the current saved paper is complete and no old signature packet or active round conflicts.
  • Confirm counterparty name and email using the approved out-of-band process.
  • Prepare one round and compare the displayed base version/hash to the intended paper.
  • Treat the temporary portal URL as a secret; copy it once to the approved delivery path.
  • Use manual delivery unless automated negotiation mail has separate acceptance evidence.
  • Record only a bounded message/provider reference; never claim it proves recipient receipt.

Before promoting a redline #

  • Confirm the submission belongs to the latest active round and has a clean, ready, policy-eligible state.
  • Download the exact returned file from Notice and check its full SHA-256.
  • Review tracked changes, comments, formatting, schedules, headers/footers, fields, and hidden content in Word.
  • Enter complete reviewed text for exactly this one attachment—never combine sources.
  • Record who reviewed, how binary features were checked, and why the text is intended.
  • Use the line comparison as an aid only, then explicitly promote or reject.
  • After promotion, confirm the new version/hash and route fresh approvals.

Before signature #

  • Confirm all required current lanes approved the exact current version and material basis.
  • Confirm delegated authority outside the product; workspace permission is not signing authority.
  • Confirm the DocuSeal template is non-public/non-archived and each exact ordered role has a required signing field; enter a name and unique normalized email for every role, while names may repeat.
  • Create one secure packet only; reconcile the existing packet if mapping or status is uncertain.
  • After completion, verify signed artifact evidence and that stale paper did not activate the contract.
  • Create confirmed, eligible-owner renewal, notice, reporting, and other schedules from the signed agreement; verify recurrence, reminders, and completion evidence.

15 · Glossary & deeper docs

Shared language for a clean handoff #

These terms help business users, Legal, implementers, security, records, and operations discuss the same thing.

Agreement / contract record
The governed Notice record connecting paper, metadata, approvals, signature, obligations, and evidence.
Working version
An immutable saved text or Markdown version in private storage, identified by version number and SHA-256.
Source document
An uploaded original or returned binary retained with filename, type, size, hash, scan state, and lineage.
Review round
One hash-bound outbound copy, recipient context, scoped return path, submissions, human decisions, and resolution.
Portal token
An expiring bearer credential for one scoped external round. The durable round stores its hash, not reusable plaintext.
Promotion
The explicit act of turning human-reviewed text tied to one clean returned source into the next immutable working version.
Workspace role
One of five lowercase server permission sets: admin, legal, requester, approver, or viewer.
Approval lane
A capitalized request label such as Legal or Finance. It is not the same as a workspace role.
Material basis
The current paper and material agreement data to which approval and signature eligibility are bound.
Outbox
Durable asynchronous delivery work with independent mail and CRM ledgers, retries, acceptance, and dead state.
Readiness
A redacted technical preflight of repository capabilities and required customer configuration. It is not business acceptance.
Audit evidence
Server-attributed events, hash-chain state, record data, document hashes, approval/signature evidence, and signed export envelopes.
