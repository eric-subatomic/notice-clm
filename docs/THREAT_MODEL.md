# Notice threat model

## Scope and status

This model covers the Notice React/vinext Worker, signed Cloudflare Access identity boundary and optional trusted-header compatibility edge, D1/R2 storage, browser client, enterprise configuration/intake, governed templates/workflows/authority, repository intelligence, scanner bridge, DocuSeal adapter/webhook/optional MCP diagnostic, delivery gateway, scheduled jobs, audit/export, and retention processing.

It describes controls present in the repository and controls that only the customer/operator can provide. It is not certification. Review it for every material change to identity, tenancy, data classes, integrations, storage, deployment topology, retention, or regulatory scope.

## Assets and objectives

| Asset | Confidentiality | Integrity | Availability |
| --- | --- | --- | --- |
| Original, draft, and signed agreements | Authorized workspace/roles only | Hash/version verifiable; unauthorized replacement prevented/detected | Recoverable within approved RTO/RPO |
| Extracted terms, language, approvals, obligations | Tenant-isolated and least privilege | Authoritative server transition/attribution | Consistent with source and recoverable |
| Legal entities, counterparties, groups, custom fields, templates, workflows, intake, playbooks, saved views, and relationships | Authorized workspace/roles only | Versioned, tenant-bound, type/digest/pin/relationship integrity; published artifacts immutable | Recoverable with the matching schema/release |
| Repository fragments, citations, extraction proposals, and ingestion inventory | Document/admin permissions only | Pinned to immutable document ID/version/hash; source-text digest, offsets, content, and extractor identity are caller-asserted; internal citation consistency, required human working-paper verification, and no-application blocker | Search/review remains available without pretending provenance or correctness was established |
| User, membership, role, workspace | Minimal disclosure | Derived from verified identity and authorized admin change | Available/fail-closed on every protected request |
| Audit, signature, export evidence | Restricted to authorized roles | Server-authored, chain/signature verifiable, independently retainable | Exportable/retained for policy duration |
| Integration and job credentials | Never in client, repo, log, or export | Scoped, rotated, and source-authenticating | Recoverable without silent verification gap |
| Counterparty portal capabilities and reply aliases | Bearer URLs disclosed only to the intended recipient; aliases and plaintext tokens minimized | Bound to one workspace, round, immutable outbound hash, expiry, and durable round-scoped transfer budget that survives token rotation | Revocable without silently delivering stale paper; exhausted transfer limits require a new round |
| Returned counterparty files and reviewed text | Treated as agreement data/PII and inaccessible until policy permits | Immutable source/hash lineage; only an authorized human can promote reviewed text | Quarantine and recovery do not require bypassing scan or provenance controls |
| Obligation/outbox/webhook/retention state | Operational roles only | Replay/idempotency/version/eligibility preserved | Retry/reconciliation within SLA |
| Service principals, grants, plans, decisions, and execution receipts | Exact workspace/sponsor/resource scope; oversight roles only | Signed identity, canonical digest, current authority/basis/policy, human decision, and idempotent receipt preserved | Revocable and reviewable without broadening human or machine authority |
| Backups, logs, exports | Protected at source classification | Complete, attributable, and tamper-resistant as required | Restorable/searchable within policy |

## Actors

- Authorized requester, legal operator, assigned approver, viewer, and workspace administrator.
- Registered machine service principal with one exact, expiring, human-sponsored grant; human agent-plan reviewer remains a separate actor.
- Customer identity, security, legal/compliance, records, integration, and infrastructure administrators.
- Notice operator/support personnel with explicitly approved access.
- Cloudflare Workers/D1/R2, the selected identity edge, DocuSeal, scanner, delivery/mail/CRM, observability, and backup providers.
- Intended counterparty recipient holding a scoped portal capability or generated reply alias.
- Anonymous internet client, unintended link recipient or mail scanner, malicious/compromised user, compromised provider/gateway, spoofed email sender, malicious document sender, insider, and supply-chain attacker.

## Trust boundaries and flows

1. Browser -> protected identity-aware edge -> Worker. Recommended mode carries a signed Cloudflare Access application JWT that Notice verifies. Compatibility mode carries canonical identity headers only after direct-origin blocking and header sanitation.
2. Worker identity -> D1 user/membership -> role permission. Request bodies never select workspace/actor/role.
3. Worker -> D1/R2. D1 metadata and R2 bytes are linked by tenant-prefixed opaque keys and hashes.
4. Worker -> narrowly public `/api/exchange/<token>` route -> counterparty download/upload. The 32-byte bearer token is carried only in the path, while D1 stores its SHA-256; successful representations are self-contained, no-store/no-referrer, and bound to one active round, immutable outbound hash, expiry, and durable upload/download attempt-and-byte budget. Token rotation does not reset the round budget; D1 admits at most one leased upload/scan at a time before body or R2 work.
5. Mail provider -> dedicated inbound-email gateway -> exact raw multipart bytes plus body digest/fresh HMAC -> exact generated reply alias -> replay/collision receipt -> counterparty submission. The gateway, not arbitrary message headers, derives sender, recipient, authentication, identifiers, and attachment inventory.
6. Untrusted upload -> full-byte type/hash/structural inspection (controlled UTF-8 text, bounded PDF header/trailer/xref and referenced-object linkage, balanced bounded RTF, or canonical DOCX ZIP/container plus required-OOXML-part structure) -> HMAC scan gateway -> quarantine or accepted storage -> bounded text/RTF extraction or isolated PDF/DOCX extraction/review -> authenticated human decision and explicit promotion. A rescan owns one exact five-minute D1 claim before scanner I/O; a correlated malicious verdict remains authoritative over a late or concurrent clean result.
7. Worker -> pinned DocuSeal 3.2.1 profile/template-role/required-field discovery -> one-off escaped working paper plus one-to-ten ordered, unique-email signers, bounded expiry, email 2FA, and merge request -> provider email delivery -> DocuSeal HMAC webhook -> provider/basis/signer reconciliation -> scanned signed artifact. Optional self-hosted MCP performs the exact handshake and one read-only `load_template` cross-check; mutation/open-world tools remain unreachable. Production does not return or embed signer bearer URLs.
8. Domain write -> D1 outbox/per-sink ledger -> native Worker Cron dispatch (or an explicitly approved bearer-authenticated external scheduler) -> independently signed mail gateway and included CRM gateway -> selected providers.
9. Administrator -> readiness/integration/retention/export routes -> external protected evidence/backup systems.
10. Signed Cloudflare Access app JWT -> registered service principal -> one exact current sponsor/grant -> action discovery or canonical plan -> a different current active Admin reviewer who may approve or reject -> independently revalidated idempotent execution receipt. For `agreement.read`, both the atomic execution claim and result commit fence the exact current principal, grant/action/resource/policy/time authority, agreement snapshot, and latest working document.
11. Administrator -> versioned legal-entity/counterparty/group/custom-field/template/workflow/intake/playbook/authority configuration -> exact immutable artifact and authority predicates -> agreement/intake/approval use.
12. External or human extractor -> caller-registered fragments/citations/proposals pinned to an immutable working-version ID/version/hash and asserted source-text digest -> human comparison with protected working paper -> attributable review -> durable application blocker; no proposal path mutates agreement/custom-field data.

## Important residual properties

### Identity

The recommended Cloudflare Access mode cryptographically validates the signed application JWT, exact issuer/audience, time, type, subject, and email before authorization. The optional trusted-header compatibility mode still depends on a separately reviewed edge that blocks direct origin access and strips caller identity headers; `NOTICE_TRUST_IDENTITY_HEADERS=true` must never be copied blindly between environments.

### Approval authority

Approval lane labels are not lowercase workspace roles. Published workflow definitions can select lanes from exact agreement facts, while active authority records grant a direct user or active group one lane in one currency with an optional minor-unit ceiling. Claim and decision repeat the authority predicate at commit. If any active or revoked authority record exists for a lane, an unmatched user fails closed; only a lane with no authority history uses the narrow compatibility mapping (`admin`/`legal` for `Legal`, `admin`/`approver` for `Finance`, and `admin` otherwise). These controls enforce the matrix the customer records, but cannot establish that the customer's delegation itself is legally valid or complete.

### Audit evidence

An agreement event hash binds event ID, workspace, agreement, sequence, type, verified actor, detail, time, and prior hash. Verification detects altered retained fields, broken links, duplicates, and gaps. It cannot prove from the remaining database that an attacker removed the latest event unless a previous head/export is held elsewhere. Export HMAC is symmetric and inherits key-custody risk.

### Integrations

Notice implements a pinned DocuSeal 3.2.1 profile plus generic scanner/mail protocols. The scanner protocol optionally carries one exact deployment-selected customer-hosted OCR model/profile; the customer supplies the private engine/runtime and Notice never contacts it directly or accepts fallback output. Its optional DocuSeal MCP path is diagnostic-only and invokes exactly one read-only `load_template` cross-check after validating the handshake and tool metadata; it is not an agent execution channel. Its separately deployed CRM gateway verifies signed canonical events, persists idempotent/version-fenced receipts, and includes HubSpot private-app, Salesforce client-credentials, and signed custom-webhook adapters. Customers retain authority over provider accounts, model weights/licenses, entitlements, least-privilege credentials, approved objects/fields/mappings, data minimization, monitoring, and provider-side reconciliation.

### Repository intelligence

Repository search and extraction proposals are evidence transport, not an autonomous legal reviewer. Literal results expose registered fragment text, offsets, fragment/source-text digests, and the immutable document version/hash to which the caller pinned them. Notice does not derive that text from or compare it with canonical working-paper bytes; the registered provenance can be wrong or adversarial even when internal hashes and citation slices match. A reviewer must compare every cited passage with the protected working paper. Human acceptance writes an audit event and permanently leaves application blocked; agreement/custom-field data is unchanged. A future provider or executor is a new trust boundary and must preserve tenant scope, source verification, human authority, idempotency, and independently reviewable mutation evidence.

### Counterparty exchange

The portal is intentionally a possession-token boundary, not an authenticated counterparty account. A valid token discloses only the round metadata and exact outbound paper and accepts a bounded return; it does not authorize any human application route, prove the sender's mailbox identity, or permit promotion. Durable D1 budgets apply to the round across token rotations: at most 10 upload attempts (at most 4 accepted and at most 6 rejected/failed), 96 MiB cumulative multipart bytes, 20 download attempts, and 256 MiB cumulative outbound bytes, with only one 21 MiB/five-minute upload work lease. Current counters are not disclosed. A busy lease returns `429` with `Retry-After: 5`; exhausted limits return `429` and require a new round. Keep the token out of logs, analytics, referrers, tickets, screenshots, URL inspection services, and unrelated redirectors. Because enterprise mail systems may rewrite or prefetch links, acceptance testing must cover the customer's actual mail path and verify that a GET never consumes the token.

Inbound email adds source authentication for the gateway request, not a legal conclusion about the sender or attachment. Notice authenticates the raw bytes and signed provider-derived evidence, fences replays and collisions, and separates `sender_review`, quarantine, rejection, and `ready`. Only an authenticated `legal` or `admin` member with `document:manage` can mark reviewed evidence ready or promote it. The customer still owns mailbox authentication policy, authorized reviewer identity, Word-review procedure, acceptable negotiating position, and any required dual control.

### Retention

Primary D1/R2 automation is only one part of deletion. The guarded D1 batch creates a `purge_jobs` manifest and emits `retention.d1_purged` while R2 is deliberately `storage_pending`; only the job manifest/result records final object cleanup. Backups, logs, exports, external evidence, search/indexes, DocuSeal, mail, CRM, and gateway records have independent retention systems. A customer deletion promise must account for all of them.

## Deployment controls not representable in source

- identity-edge access policy, direct-origin blocking, canonical header sanitation, MFA, conditional access, and session lifecycle.
- D1/R2 private access, environment separation, region, encryption/key policy, backup, restore, capacity, and disaster recovery.
- Managed-secret store, rotation, deployment identity, branch/environment protection, and artifact provenance.
- WAF/DDoS and distributed cross-round/verified-user/IP limits, egress/network restrictions, and DNS controls; these complement the application-enforced per-round portal budgets.
- Protected logs/metrics/traces/SIEM, alerting, on-call, incident communications, status page, and support access.
- Scanner/DocuSeal/delivery/mail/CRM, the optional customer-hosted OCR profile/runtime, repository extractors, subprocessors, credentials, mappings, provider-side logs, and reconciliation.
- Records schedule, legal-hold authority, backup expiry, independent/WORM evidence, offboarding/deletion approval.
- Penetration test, privacy/legal/compliance/vendor-risk assessment, SLA, and accepted residual risk.

## Required verification

Before real-data use retain evidence for:

1. anonymous, malformed identity, direct-origin/header spoof, disabled user, cross-role, cross-workspace, IDOR, and mass-assignment cases;
2. requester/decider separation, governed workflow condition/digest/snapshot integrity, direct/group lane authority, exact currency/amount ceilings, group disable/removal, revoked-record fallback cutoff, stale paper/material/workflow basis, unassigned/cross-lane claim races, legacy unattributed approvals, agent sponsor/reviewer separation for both decisions, current active-Admin decision-commit checks, and `agreement.read` exact authority/time/agreement/latest-document claim and completion races;
3. session expiry/revocation, origin/CSRF/CORS, download/cache/header, and export authorization;
